# 发版流程

写给执行发版的人或模型。前半部分是通用流程，最后一节是本仓库的具体约定。

## 原则

- 发版只改版本号，不夹带别的改动。需要先修的东西（例如失败的测试）单独提交，放在发版提交前面。
- 推送、强推、发布到包仓库都是对外的、撤不回的操作。用户要求发版就是授权了发布本身；但要定版本号、重写已推送的历史、或者流程里出现用户没预料到的事，先停下来说明，由用户决定。
- 每一步都要有能检查的结果。不确定做没做对，就去查，不要猜。

## 1. 确认起点

- 工作区干净，在发版分支上，和远端同步。
- 查清上一次发版发到哪里：上一个发版提交、各包在包仓库里的最新版本。tag 可能不全，不要只看 tag。
- 如果之前已经做过一部分（版本号改了、tag 打了、某个包发了），先查清每一步的实际状态，再接着做。

## 2. 确定要发哪些包

- 用户点名的包要发。
- 被它依赖、而且自上次发版以来改过源码的内部包，也要发新版本。否则发出去的包依赖的是没有这些改动的旧版本。
- 自上次发版以来没有改动的包，不发。
- 版本号按 semver 定：删除或修改已公开的接口是不兼容改动，只增加是新功能，只修 bug 是补丁。拿不准、或者项目还在 0.x，就列出改动问用户。

## 3. 改版本号

版本号可能不止写在包的清单文件里，还会出现在：

- 代码里的版本常量，以及检查它的测试；
- lockfile 里 workspace 包的条目（有些工具不会自动更新）；
- 文档、更新日志。

全仓搜索旧版本号，确认每一处是该改还是本来就该保留旧值。改完后，用 CI 使用的同一种严格模式重新安装依赖（例如 frozen lockfile），确认 lockfile 一致。

## 4. 检查

- 本地跑完整检查：类型检查、测试、构建，以及发布产物的冒烟测试（如果有）。
- 再在 CI 上跑一次，覆盖所有支持的平台，跑在**将要发布的那个提交**上。
- 本地和 CI 结果不一致时，先找环境差异：操作系统、终端是不是 TTY、`NO_COLOR` 等环境变量、工具版本、机器快慢。修复的是测试本身的问题还是产品的问题，要分清楚，并告诉用户。

## 5. 提交和 tag

- 发版提交的信息写上这次发的每个包和版本号。
- tag 打在发版提交上。打完确认它指向哪个提交；之后如果改了发版提交，要移动 tag。

## 6. 推送

- 先推送提交，再推送 tag。
- 需要改动已推送的历史时：先建备份分支；重排后比较新旧提交，代码 diff 必须为空，除非用户就是要改代码；强推用 `--force-with-lease` 并指定远端原来的提交，不要用 `--force`。

## 7. 发布

- 按依赖顺序发布：被依赖的包先发。
- 使用项目规定的发布命令，可以先 dry-run，确认打包的文件和版本号。
- 账号开了二次验证时，发布命令会等待浏览器确认，模型无法替用户完成。两个办法：让用户自己运行命令；或者用户提供一次性 token，只通过那条命令的环境变量传入，用完删除，不写进任何文件，发完提醒用户撤销。
- 发布命令报告成功，就不要因为暂时查不到新版本而重新发布。

## 8. 确认

- 包仓库可能要几分钟才能查到新版本，客户端查询还有缓存，要直接问包仓库。
- 查看发布出去的清单：版本号对不对，内部依赖是不是指向这次发的版本，不能是 workspace 协议的写法，也不能是旧版本。

## 9. 发布说明

- 如果项目在代码托管平台上发 release（例如 GitHub Release），在 tag 推送之后创建，基于这个 tag，并且只基于已经推送的 tag。
- 格式照上一次的 release 写：先看上一次的标题和正文，保持一致。
- 内容从上次发版以来的提交里整理：写用户能感知的变化，按主题分组。只改测试、文档、发版的提交不写。不兼容的改动要写明，并说明怎么迁移。
- 写清楚怎么安装这个版本，以及同时发布了哪些包。

## 10. 汇报

告诉用户：

- 发了哪些包、各是什么版本；
- 发布说明的链接；
- 推送了哪些提交，tag 指向哪个提交，有没有强推；
- 检查和 CI 跑在哪个提交上，结果如何；
- 还剩哪些事没做，例如包仓库还没同步、token 要撤销、CI 要重跑。

## 本仓库的约定

- **工具**：bun workspace。包之间的依赖写成 `workspace:*` / `workspace:^`，发布时由 bun 换成本地的版本号。所以只能用 `bun publish`，各包的 `prepublishOnly` 会拒绝 `npm publish`，并在发布前自动构建。
- **检查**：在仓库根目录运行 `bun install --frozen-lockfile`、`bun run typecheck`、`bun test`、`bun run build`、`bun run smoke:node`。CI 在 `.github/workflows/ci.yml`，只能手动触发（`gh workflow run ci.yml`），在三个系统上运行。
- **lockfile**：`bun install` 不会更新 `bun.lock` 里 workspace 包的 `"version"`，要手动改。
- **版本常量**：`uncarved` 的版本还写在 `packages/kernel/src/plugin.ts` 的 `KERNEL_VERSION`，以及它的测试里；`@uncarved/jade-api` 的版本还写在 `apps/jade/src/api.ts` 的 `API_VERSION`，有测试检查两者一致。
- **依赖顺序**：`uncarved` → 其他 `@uncarved/*` 包 → `@uncarved/jade`。
- **提交信息**：`Release <包> <版本>, <包> <版本>`，例如 `Release jade 0.3.1, jade-api 1.2.0`。
- **tag**：只给 jade 打，格式是 `jade-v<版本>`。
- **GitHub Release**：只给 jade 发，标题是 `jade v<版本>`，正文用中文，写法照上一次。创建命令：`gh release create jade-v<版本> --title "jade v<版本>" --notes-file <文件> --verify-tag --latest`。
- **查询 registry**：

  ```sh
  curl -s "https://registry.npmjs.org/<包名，/ 写成 %2f>/<版本>"
  ```
