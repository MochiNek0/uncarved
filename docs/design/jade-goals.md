# 目标：jade

> 状态：2026-11-09 写下。目前只有作者一个人在用 jade；处境变了（有了别的用户、有人拿它改造）时回来更新。
>
> 怎么做见 [jade.md](./jade.md)，内核的约束见 [CONSTITUTION.md](../../CONSTITUTION.md)。这里只说为什么做、先做什么。

## 1. 总目标

把 jade 做成一个**一切功能都是插件**的编程 agent：核心小而稳定，不认识任何功能；shell、文件、审批、提示词、界面、模型都是普通插件。坏一个插件只伤到它自己，想换掉哪项能力，装个插件就行。

## 2. 三个方向

| | 目标 | 做到了是什么样 |
|---|---|---|
| **A** | 作者自己每天主力用的编程 agent | 干活时不再切回别的工具 |
| **B** | 别人拿去改造的发行版：不 fork，只装插件 | 有不认识的人在上面写插件、做自己的版本 |
| **C** | 证明 uncarved 内核和宪法这套架构是对的 | 真实功能都能用插件做出来，故障隔离、可重放经得起检验 |

## 3. 先后：用 A 带动 B 和 C

三个方向不冲突，但现在只有 A 有真实的反馈：每天用，做对做错马上知道。B 没有外部用户，做了什么都没人说对不对；C 要靠真实功能来检验。所以：

1. **先把 jade 做成作者离不开的工具。** 优先级按日常使用里碰到的真实问题排。想切回别的工具、觉得哪里别扭时，把原因记进 [jade-log.md](./jade-log.md)，这份清单就是路线图。
2. **新功能都写成普通插件。** 每做一个功能，就顺带检验了插件接口（B）和架构（C）。接口哪里别扭，作者是第一个碰到的人。
3. **B 的准备就是守住接口质量。** 不先设计"公司版"这类产品形态；有人要改造 jade 时，他需要的是好用、稳定、有文档的插件接口。
4. **C 随手记。** 碰到"多亏是插件才能这样做"或"架构挡了路"的时候，记进 [jade-log.md](./jade-log.md)。前者是架构的证据，后者是该改架构的证据。

## 4. 不做什么

- **不替想象中的用户提前做产品。** 碰到新方向，不管是谁提的（包括 AI），先问："谁会用？怎么知道他需要？"答不上来就先不做。
- 例子：公司版（审计、网关、网页审批，`approval-audit` 分支上的 acme 示例）是 AI 提的方向，没有真实用户要，没有合进 main。
