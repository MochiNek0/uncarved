# 设计：进程外 hook（宪法 5.5）

> 状态：已评审，实施中 · 2026-10-29
>
> 对应条款：5.5（声明字段、出错即失败、强制超时）、7.1（项目层可执行配置需确认）、7.3（只能通过协议影响内核）、I-9（一切可中断）

## 1. 目标与不做的事

目标：让插件可以用任何语言写、运行在独立进程里，同时内核仍然能保证 5.5 的三条约束。

不做：

- 进程外**工具**。一个进程内插件已经可以包装任意外部工具服务（例如 MCP），不需要内核支持。等有三个发行版需要时再议（1.3）。
- 自动重启、重试。重试属于策略（第九章）。
- 进程外插件之间的通信。

## 2. 分层：约束在内核，传输在内核外

```
┌──────────── 内核 uncarved ────────────┐      ┌── @uncarved/plugin-stdio ──┐      ┌─ 插件进程 ─┐
│ RemoteHook 规范：                       │      │ 启动子进程、JSON-RPC 编解码  │ stdio│ 任意语言   │
│  · 只发送 reads 中的字段                │◄────►│ 把进程声明的 hook 翻译成     │◄────►│            │
│  · 只接受 writes 中的字段               │      │ RemoteHook，交给内核         │      │            │
│  · 超时必须有限，不能 optional           │      │ 首次加载前走 7.1 确认        │      │            │
│  · 取消信号转发                         │      └────────────────────────────┘      └────────────┘
└────────────────────────────────────────┘
```

理由：5.5 的三条是**内核的保证**，不能依赖每个传输实现自己遵守，所以字段裁剪、合并、超时都放在内核里。启动进程、编解码这些和具体传输相关，放在内核外（第九章：内核不包含 UI、存储后端，同理不包含进程管理）。以后要加 WebSocket、HTTP 传输，只需要新写一个包，约束不用重新实现。

## 3. 内核侧：RemoteHook

`HookSpec` 增加一个变体。内核拿到它以后自己负责裁剪和合并，传输层只负责把裁剪后的数据送过去、把回复拿回来：

```ts
interface RemoteHookSpec {
  kind: "transform" | "gate" | "observe"
  point: ExtensionPoint
  remote: true
  reads: string[]          // 顶层字段名，见第 4 节
  writes: string[]         // 只有 transform 可以非空，且必须是该扩展点允许写的字段
  timeoutMs: number        // 必填，有限正数
  order?: number
  call(payload: Record<string, unknown>, ctx: RemoteContext): Promise<unknown>
}
```

注册时（`Runtime` 构造时）检查，不满足就拒绝加载插件（`PluginIncompatible`），不静默降级（8.2）：

| 检查 | 对应条款 |
|---|---|
| `timeoutMs` 是有限正数 | 5.5 第 3 款 |
| 没有 `optional` | 5.5 第 2 款 |
| `reads`/`writes` 都是该扩展点已知的字段；`writes` 只含允许写的字段 | 5.5 第 1 款 |
| gate 和 observe 的 `writes` 为空 | 5.1 |

调用时：

1. 从完整的值中只取 `reads` 列出的字段，深拷贝后交给 `call`。
2. transform 的回复必须是只包含 `writes` 中字段的对象。出现任何其他字段，视为该 hook 出错。理由：静默丢弃会掩盖插件的 bug，而且出错即失败正是 5.5 第 2 款的精神。
3. 合并：`{ ...原值, ...回复 }`，然后照常经过现有的检查（例如 I-6 模型块不可改写），失败同样归咎于这个 hook。
4. 超时、取消、进程崩溃都按"出错"处理：transform 使本轮失败，gate 视为 `deny`，observe 记录错误。和进程内 hook 完全一致（5.1）。

## 4. 各扩展点的字段

只到顶层字段，不支持嵌套路径。宪法的例子"只需要 `system` 段"用顶层字段就能表达，嵌套路径会让合并规则变复杂。

| 扩展点 | 可读字段 | 可写字段 |
|---|---|---|
| `context.project` | `messages` | `messages` |
| `context.build`、`model.before` | `system` `messages` `tools` `ext` | `system` `messages` `tools` `ext` |
| `tool.before` | `toolUseId` `name` `input` | `input` |
| `tool.after` | `call` `content` `isError` | `content` `isError` |
| `tool.gate` | `toolUseId` `name` `input` `tool` | — |
| `turn.continue` | `phase` `messages` `derived` | — |
| `model.after` | `model` `content` `stopReason` `usage` | — |
| `event` | `type` `seq` `at` `data` `origin` | — |
| `session.start`/`session.end` | `sessionId` `phase` `plugins` | — |

`context.project` 的值本身是数组，传输时包成 `{ messages }`，其他扩展点不变。

另有一个上下文字段 `derived`（派生数据快照），只有在 `reads` 中显式列出时才发送。

## 5. 协议（`@uncarved/plugin-stdio`）

JSON-RPC 2.0，经子进程的 stdin/stdout 传输，一行一条消息（NDJSON）。stderr 不属于协议，作为日志转发给订阅者。

### 内核 → 插件

| 方法 | 参数 | 回复 |
|---|---|---|
| `initialize` | `{ kernel: string, capabilities: string[] }`（kernel 为内核版本，如 `"0.1.0"`） | 插件清单，见下 |
| `hook` | `{ hook: string, sessionId: string, payload: object }` | transform：只含可写字段的对象；gate：`{ decision, reason? }`；observe：`{}` |
| `$/cancel` | `{ id }`（通知，无回复） | — |
| `shutdown` | `{}` | `{}`，之后内核关闭 stdin |

`initialize` 的回复：

```json
{
  "id": "acme/redact", "version": "1.2.0", "kernel": "^0.1",
  "needs": ["transform:tool.after"], "resume": "ask",
  "hooks": [
    { "name": "redact", "kind": "transform", "point": "tool.after",
      "reads": ["content"], "writes": ["content"], "timeoutMs": 5000 }
  ]
}
```

observe 也用带 `id` 的请求而不是通知：这样超时可以计时，错误可以记录，慢的插件不会让管道无限积压。

### 插件 → 内核（只在某次 `hook` 调用进行中有效）

| 方法 | 参数 | 需要的能力 |
|---|---|---|
| `log/record` | `{ call, key, value }` | `log:record` |
| `log/emit` | `{ call, type, data }` | `log:emit` |

`call` 是正在进行的那次 `hook` 请求的 `id`。调用已结束或能力未声明时返回错误。这就是 7.3 说的"只能通过协议暴露的能力影响内核"：插件进程拿不到会话状态，只能在 hook 调用期间使用这两个方法。

### 生命周期

- 由使用者创建和关闭：`const p = await spawnPlugin({ command, args, cwd })` 返回一个普通的 `Plugin`，用完调用 `p.close()`。内核不管理进程。
- 一个进程可以服务多个会话，每次调用带 `sessionId`。
- 进程退出后，所有进行中和之后的调用都按出错处理。**不自动重启**（第九章：重试是策略）。`p.exited` 在进程退出时 resolve，带上退出码，发行版据此决定是否自己重新 `spawnPlugin`。版本可能已经变化，恢复会话时照常走 4.6。
- 取消（I-9）：`signal` 触发或超时时发送 `$/cancel`。之后迟到的回复直接丢弃。

## 6. 信任（7.1）

项目层的进程外插件属于"可执行配置"，首次启动前必须确认。确认的内容哈希包括：

- 启动规格（`command`、`args`、`env`，按键排序后序列化）
- `cwd` 目录的内容哈希（复用 `hashDir`），如果 `cwd` 在项目目录内

为此把 `loadProjectPlugin` 中"查记录、询问、保存"的部分抽成内核导出的 `requireTrust({ hash, path, files }, { trust, confirm })`，两处共用。`spawnPlugin` 在 `layer: "project"` 时必须先调用它，否则 Runtime 照样会拒绝这个项目层插件（与 7.1 已有的机制一致）。

## 7. 实现步骤

1. 内核：`RemoteHookSpec` 及注册检查、字段裁剪与合并；抽出 `requireTrust`。用进程内的假 `call` 测试，不涉及子进程。
2. `@uncarved/plugin-stdio`：JSON-RPC 编解码、`spawnPlugin`、取消、崩溃处理。用一个测试用的插件脚本（Bun 运行的 .ts 文件）做端到端测试。
3. 宪法：5.5 补充字段表的出处和"回复含未声明字段视为出错"，如果评审通过的话。

## 8. 评审结论

原则：拿不准时先取严格、小的一边。以后放宽是兼容修改，收紧则会破坏已经依赖宽松行为的插件。

| # | 问题 | 结论 | 未采用 |
|---|---|---|---|
| 1 | 字段粒度 | 只到顶层字段 | 支持 JSON Pointer 嵌套路径 |
| 2 | 回复包含未声明的字段 | 视为出错 | 静默丢弃 |
| 3 | 进程崩溃 | 不自动重启，之后的调用都失败 | 内核自动重启一次 |
| 4 | observe 的传输 | 带回复的请求 | 通知（更快，但无法计时、无法背压） |
| 5 | 进程外工具 | 不做，由进程内插件包装 | 协议里增加 `tool/execute` |
